# Why broken LoRA synchronization makes GRPO off-policy

A precise statement is: **the first optimizer update is usually valid. The next
GRPO rollout becomes off-policy if vLLM ignores the updated LoRA.**

## The four policies involved

It helps to distinguish these policies:

| Name | Purpose |
|---|---|
| Actor/current policy | The PEFT model being trained. |
| Rollout policy | The vLLM model that generates the responses for each prompt. |
| Old policy | The actor immediately before the current PPO/GRPO update; used in the probability ratio. |
| Reference policy | The frozen base model used for the KL penalty. |

The reference policy being the base model is intentional. The problem is when
the rollout policy accidentally remains the base model too.

## What LoRA changes

With full fine-tuning, training modifies the main model weights:

$$
W \rightarrow W'
$$

With LoRA, the base weights remain frozen and the effective weight is:

$$
W_{\text{effective}} = W + \frac{\alpha}{r}BA
$$

Here:

- $W$ is the frozen Gemma 4 base weight.
- $A$ and $B$ are small trainable LoRA matrices.
- Only $A$ and $B$ are updated by the optimizer.

Therefore, verl does not need to copy the entire model to vLLM after every
step. It should:

1. Load the frozen $W$ into vLLM once.
2. Send the current LoRA $A$ and $B$ after every optimizer step.
3. Tell vLLM to generate with $W + BA$.

The third step is what currently fails for Gemma 4 in unpatched vLLM.

## First GRPO iteration

A newly initialized LoRA normally starts as:

```text
A = random
B = zero
BA = zero
```

Initially, all three relevant models are therefore equivalent:

```text
Actor effective model = W + 0 = base model
vLLM broken LoRA model = W
Reference model        = W
```

The first iteration is approximately correct:

```text
1. vLLM generates responses from W
2. Rewards are calculated
3. Rewards are normalized within each response group
4. Actor log-probabilities are calculated under W
5. GRPO updates A and B
```

After the optimizer update, suppose the actor is now:

$$
\pi_1 = W + \Delta W_1
$$

The first batch was generated by $W$, which was also the actor at the time of
generation, so there is no behavior-policy mismatch yet.

If training resumes from an already-trained LoRA, this grace period does not
exist: the policies differ from the first rollout.

## What should happen after the update

verl performs a weight synchronization after updating the actor:

```text
Actor LoRA A₁/B₁
       |
       v
TensorLoRARequest
       |
       v
vLLM installs A₁/B₁
```

The desired state before iteration 2 is:

```text
Actor policy   = W + ΔW₁
Rollout policy = W + ΔW₁
Reference      = W
```

vLLM would then sample from the same policy whose probabilities verl uses as
the old policy.

## What actually happens with the Gemma 4 bug

The adapter tensors reach vLLM and initially load into the correct modules.
However, vLLM subsequently visits aliased names for the same physical Gemma 4
decoder modules and resets their LoRA buffers.

The effective state becomes:

```text
Actor policy   = W + ΔW₁
Rollout policy = W             <-- LoRA silently removed
Reference      = W
```

The synchronization mechanism ran, and the adapter may even appear registered,
but the adapter has no effect during inference.

## The vLLM alias-reset bug, object by object

The problem is not that Gemma 4 has two copies of every decoder layer. It has
one physical layer object reachable through more than one Python module name.
Conceptually, its construction looks like this:

```python
layers = [layer_0, layer_1, ..., layer_34]

# These lists contain references to the same objects, not copies.
self_decoder.decoder_layers = layers[:15]
cross_decoder.decoder_layers = layers[15:]
```

For example, the same physical QKV projection in layer 0 is reachable as both:

```text
language_model.model.layers.0.self_attn.qkv_proj
language_model.model.self_decoder.decoder_layers.0.self_attn.qkv_proj
```

The two names have the same Python object identity:

```text
id(module_at_first_name) == id(module_at_second_name)
```

The alias is useful for Gemma 4's YOCO/KV-sharing forward path. It becomes a
problem because vLLM deliberately discovers LoRA targets with:

```python
model.named_modules(remove_duplicate=False)
```

Ordinary `named_modules()` suppresses repeated objects. With
`remove_duplicate=False`, vLLM records both names. In the local vLLM 0.21
probe, this produced 422 LoRA-capable names for approximately 212 physical
linear modules; 210 physical modules appeared under at least two names.

The adapter, however, has weights under the normal checkpoint name. After
vLLM's packing of separate PEFT projections, an example is:

```text
adapter contains:
  language_model.model.layers.0.self_attn.qkv_proj

adapter does not contain a second copy named:
  language_model.model.self_decoder.decoder_layers.0.self_attn.qkv_proj
```

That absence is correct. There is only one physical projection and therefore
only one LoRA weight should be needed.

vLLM 0.21 activates an adapter by iterating over every registered *name*:

```python
for module_name, module in self.modules.items():
    module_lora = find_adapter_weight(module_name)
    if not module_lora:
        module.reset_lora(slot)
    else:
        module.set_lora(slot, module_lora.A, module_lora.B)
```

Suppose `Q` is the one physical layer object and slot 0 is the adapter slot:

```python
modules = {
    "model.layers.0.self_attn.qkv_proj": Q,
    "model.self_decoder.decoder_layers.0.self_attn.qkv_proj": Q,
}
```

Activation then proceeds as follows:

| Visit | Name lookup | Operation on physical object `Q` | Slot 0 afterward |
|---|---|---|---|
| 1 | canonical name has a weight | `Q.set_lora(0, A, B)` | nonzero `A`, `B` |
| 2 | alias name has no separate weight | `Q.reset_lora(0)` | zeros |

`reset_lora()` literally fills that slot's `lora_a_stacked` and
`lora_b_stacked` buffers with zero. Because both names point to `Q`, the second
operation erases the weights installed by the first operation. The forward
path also calls this same `Q` object, so it observes the zeroed buffers and
computes only the base projection.

Resetting modules for which an adapter has no weights is normally necessary.
For example, switching from an adapter that targets attention and MLP layers
to an attention-only adapter must clear stale MLP values in the reused slot.
The bug is doing this decision independently for aliases of one physical
module.

This also explains why several superficial checks can pass:

- The adapter request reaches vLLM.
- Adapter parsing and PEFT-to-vLLM name conversion succeed.
- Separate `q_proj`, `k_proj`, and `v_proj` tensors can be packed into
  `qkv_proj` successfully.
- The adapter ID can be registered and marked active.
- `set_lora()` can actually be called with nonzero tensors.
- A later alias visit nevertheless zeroes the same physical buffer.

The robust fix is to consolidate entries by physical object identity first,
prefer a name that has adapter weights over aliases that do not, and call
`set_lora()` or `reset_lora()` exactly once per physical module:

```python
choice_by_object = {}
for module_name, module in modules.items():
    weight = find_adapter_weight(module_name)
    key = id(module)
    if key not in choice_by_object or weight is not None:
        choice_by_object[key] = (module, weight)

for module, weight in choice_by_object.values():
    if weight is None:
        module.reset_lora(slot)
    else:
        module.set_lora(slot, weight.A, weight.B)
```

Merely changing the discovery call to `remove_duplicate=True` is less robust:
it retains whichever alias PyTorch visits first, and that retained name might
not be the name used by the adapter. Adding more leaf names to
`target_modules` also does not solve the identity problem; the synchronization
path would still need to manufacture duplicate adapter keys for aliases of the
same object.

## Second GRPO iteration

The policy mismatch now matters:

```text
1. vLLM generates responses from W
2. Rewards describe the quality of responses sampled from W
3. verl recomputes "old" log-probabilities using W + ΔW₁
4. The actor is updated as though those responses were sampled from W + ΔW₁
```

In notation, the responses are actually sampled from:

$$
y \sim \pi_{\text{rollout}} = \pi_{\text{base}}
$$

but verl treats the data approximately as if:

$$
y \sim \pi_{\text{old}} = \pi_{\text{LoRA},1}
$$

That assumption is false.

## Why the PPO probability ratio does not repair it

GRPO/PPO uses a ratio resembling:

$$
\rho =
\frac{\pi_{\theta}(y \mid x)}
     {\pi_{\text{old}}(y \mid x)}
$$

This controls how far the actor moves from the actor that supposedly generated
the samples.

The actual generator in this case was a third policy:

$$
q(y \mid x) = \pi_{\text{base}}(y \mid x)
$$

The default loss does not include the correction needed for that mismatch:

$$
\frac{\pi_{\text{old}}(y \mid x)}
     {q(y \mid x)}
$$

At the beginning of an update, $\pi_\theta$ and $\pi_{\text{old}}$ are the same
actor, so the PPO ratio is near 1. That does not mean the data are on-policy. It
only means the new and old actor snapshots agree; both are being evaluated on
samples produced by a different model.

In this experiment, `calculate_log_probs: True` makes vLLM return its rollout
log-probabilities. verl compares those probabilities with the actor
probabilities for diagnostics, but by default it recomputes and trains against
the actor's `old_log_probs`. The comparison detects the mismatch; it does not
automatically correct it.

## How to read the mismatch in W&B

### What is being compared

There is one generated response token sequence, produced by vLLM:

```text
y1, y2, y3, ..., yT
```

For each actual response token `yt`, verl has two scores:

```text
rollout_log_probs[t] = log q(yt | prompt, y<t)       # reported by vLLM
old_log_probs[t]     = log pi_old(yt | prompt, y<t)  # recomputed by actor
```

Thus, the diagnostic asks whether vLLM and the actor assign the same
probability to the **same token with the same prefix**. It is not comparing two
separately sampled answers.

The primary metrics are:

| W&B metric | Exact interpretation | Healthy direction |
|---|---|---|
| `training/rollout_probs_diff_mean` | Mean of `abs(exp(old_log_probs) - exp(rollout_log_probs))` over response tokens | close to the run's step-1 baseline |
| `training/rollout_probs_diff_std` | Spread of those absolute probability differences | low |
| `training/rollout_probs_diff_max` | Largest difference on any response token | low, but noisy and not useful alone |
| `training/rollout_actor_probs_pearson_corr` | Correlation of actor and vLLM probabilities over response tokens | close to 1 |
| `training/rollout_probs_diff_valid` | Whether the tensors had compatible shapes and the calculation ran | 1 only means the diagnostic is valid; it does **not** mean the policies match |

For a concrete token, suppose vLLM generated `aspirin` and reported probability
0.70, while the actor recomputation gives it probability 0.20. That token adds
`abs(0.20 - 0.70) = 0.50` to `rollout_probs_diff_mean`.

The `rollout_corr/*` metrics show the same mismatch in log-probability space:

| W&B metric | Interpretation | Healthy direction |
|---|---|---|
| `rollout_corr/training_log_ppl` | Mean per-sequence, per-response-token negative log probability under the actor | overlaps rollout value |
| `rollout_corr/rollout_log_ppl` | The corresponding value reported by vLLM | overlaps training value |
| `rollout_corr/log_ppl_abs_diff` | Mean absolute per-sequence gap between the preceding quantities | close to 0 |
| `rollout_corr/ppl_ratio` | Mean per-sequence `exp(training_log_ppl - rollout_log_ppl)` | close to 1 |
| `rollout_corr/k3_kl` | Stable divergence estimator based on the actor/vLLM log-probability ratio | close to 0 |

Despite their names, the two `*_log_ppl` curves are negative log probability
per response token, averaged over sequences; smaller means the model assigned
more probability to the sampled tokens. The actual `*_ppl` metrics exponentiate
at the sequence level before taking the batch mean, so they need not equal the
simple exponential of the logged batch-average `*_log_ppl` value.

### Recommended W&B panels

Put these curves on the same step axis:

1. `training/rollout_probs_diff_mean`.
2. `training/rollout_actor_probs_pearson_corr`.
3. `rollout_corr/training_log_ppl` and
   `rollout_corr/rollout_log_ppl` together in one panel.
4. `rollout_corr/log_ppl_abs_diff`.
5. `rollout_corr/ppl_ratio`, with 1 as the desired value.
6. `rollout_corr/k3_kl`.
7. `actor/lr` and `actor/grad_norm`, to identify when LoRA first really
   changes.

Do not diagnose from `rollout_probs_diff_max` alone. Even a healthy BF16 run can
contain a rare outlier token with a large maximum while the mean and
correlation remain excellent.

### What a broken LoRA sync should look like over time

For a newly initialized LoRA, compare three moments:

```text
step 1 rollout:  LoRA contribution is zero; actor and vLLM should match
step 1 update:   optimizer makes LoRA nonzero, if lr and gradients are nonzero
step 2 rollout:  first place the synchronized nonzero LoRA can affect vLLM
```

If synchronization works, actor and rollout move together, so the agreement
metrics remain near their initial numerical baseline. If vLLM silently remains
the base model, the curves separate after the first effective update:

| Metric | Working sync | LoRA no-op in vLLM |
|---|---|---|
| `rollout_probs_diff_mean` | stays near baseline | rises as LoRA strengthens |
| Pearson correlation | stays near 1 | falls |
| actor and rollout `log_ppl` | remain overlaid | split |
| `log_ppl_abs_diff` | stays near 0 | rises |
| `ppl_ratio` | stays near 1 | departs from 1 |
| `k3_kl` | stays near 0 | rises |

There can be a one-step delay. The rollout and diagnostics at step `N` happen
before step `N`'s optimizer update, and that update's weights affect the next
rollout. This configuration also uses learning-rate warmup. If `actor/lr` is
zero at step 1, look for the first step with both nonzero `actor/lr` and a real
`actor/grad_norm`, then inspect the following rollout step.

### Calibration from the local Gemma 4 runs

The locally observed values give a much more useful scale than expecting exact
zero across different inference kernels:

| State | Probability diff mean | Pearson | Actor vs vLLM log-PPL |
|---|---:|---:|---:|
| healthy actor/vLLM agreement after both actor fixes | about 0.007 | 0.998--0.999 | approximately 0.43 vs 0.43 |
| one partially repaired run | 0.064--0.068 | about 0.84 | 0.75--0.79 vs 0.42--0.46 |
| earlier actor-side failure | 0.179--0.186 | 0.62--0.64 | about 1.53 vs 0.44--0.46 |
| old 08-26 LoRA run | 0.75--0.78 | 0.05--0.10 | actor about 13 vs rollout about 0.43 |

In the healthy run, `log_ppl_abs_diff` was about 0.002--0.003 and `ppl_ratio`
was about 1.001. For this hardware/software path, a sustained probability diff
above roughly 0.02 or a correlation below roughly 0.98 should trigger
investigation. Those are empirical guards for this setup, not universal vLLM
tolerances.

The old LoRA run is an important caution. At step 1 it already had
`rollout_probs_diff_mean = 0.7596`, correlation `0.0908`, actor
`training_log_ppl = 13.01`, and vLLM `rollout_log_ppl = 0.432`. A fresh LoRA's
`B` matrix is zero at that point, so the adapter no-op cannot explain such a
large initial disagreement. That trace diagnosed a catastrophic actor/vLLM
mismatch, later traced primarily to the separate Gemma 4 actor-forward
KV-sharing/cache issue (and, in later diagnostics, bad RoPE buffers on nonzero
FSDP ranks). It is **not** clean experimental proof of the vLLM alias-reset
bug.

The clean test for the LoRA bug is therefore:

1. Start from the actor path whose full-finetune agreement is approximately
   `0.007 / 0.999`.
2. Run a zero-initialized LoRA and verify the same step-1 baseline.
3. Confirm `actor/lr`, `actor/grad_norm`, and LoRA tensors show a real update.
4. Check the next rollout. A patched vLLM should remain near baseline; an
   unpatched no-op should drift away as the actor adapter becomes nonzero.
5. Independently compare vLLM base versus vLLM+LoRA output/logits or inspect
   the installed LoRA buffers. This distinguishes alias-reset from any other
   actor/vLLM numerical mismatch.

Reward, entropy, `actor/pg_loss`, checkpoint creation, and nonzero gradients do
not establish successful synchronization. They can all look plausible while
the actor trains and the rollout engine remains at the base model.

## A simple example

Imagine the base model chooses:

```text
Good answer: 50%
Bad answer:  50%
```

After several LoRA updates, the actor chooses:

```text
Good answer: 90%
Bad answer:  10%
```

If synchronization works, the next response groups mostly contain good
answers. Training then explores refinements among the improved actor's
behavior.

With the bug, vLLM keeps producing:

```text
Good answer: 50%
Bad answer:  50%
```

verl then scores those samples under a model that says they should occur with
90%/10% probability. The group advantages describe variation among base-model
responses, not variation under the current actor.

The gradients can still be nonzero. Training can still appear to proceed:

- Loss decreases.
- LoRA parameters change.
- Checkpoints are written.
- Rewards may fluctuate or even improve somewhat.
- The rollout distribution nevertheless never follows the learned policy.

As the LoRA becomes stronger, the actor/rollout mismatch grows.

## Why full fine-tuning works

For full fine-tuning, verl sends the actual updated $W'$ into vLLM. It does not
rely on Gemma 4's broken runtime LoRA activation:

```text
Actor W₁ --full-weight sync--> vLLM W₁
Actor W₂ --full-weight sync--> vLLM W₂
```

Each new rollout is therefore generated by the updated actor.

For LoRA, the analogous requirement is:

```text
Actor W + ΔW₁ --adapter sync--> vLLM W + ΔW₁
```

Currently the adapter synchronization completes mechanically, but unpatched
vLLM effectively evaluates $W + 0$.

Thus, "invalid" means that after the first update the run is no longer standard
on-policy GRPO and its results cannot be interpreted as such. It does not mean
the program necessarily crashes or produces zero gradients.

## Case study: what `oumi-ai/agent-finetune` actually does

The [`oumi-ai/agent-finetune`](https://github.com/oumi-ai/agent-finetune/tree/main)
repository demonstrates that Gemma 4 LoRA SFT works, but it does not demonstrate
that an unmerged Gemma 4 LoRA works in vLLM.

This was verified against the complete tracked `main` branch at commit
[`3e81f5b`](https://github.com/oumi-ai/agent-finetune/commit/3e81f5b52623ed2244296b3cc1de0cf69d01426f),
including its tracked notebooks. Searches included `vllm`, `engine: VLLM`,
`type: VLLM`, `--lora-modules`, `enable_lora`, `LoRARequest`, `adapter_model`,
`llama-server`, `--lora-scaled`, and `/lora-adapters`.

### Training uses TRL and PEFT

The E2B configuration really does train a LoRA adapter through Hugging Face:

```yaml
training:
  trainer_type: "TRL_SFT"
  use_peft: true

peft:
  lora_target_modules:
    - q_proj
    - k_proj
    - v_proj
    - o_proj
    - gate_proj
    - up_proj
    - down_proj
  lora_exclude_modules:
    - ".*vision_tower.*"
    - ".*audio_tower.*"
```

See the repository's
[`gemma4_e2b_lora_xs.yaml`](https://github.com/oumi-ai/agent-finetune/blob/3e81f5b52623ed2244296b3cc1de0cf69d01426f/training/gemma4_e2b_lora_xs.yaml#L50-L121).

This is compatible with the vLLM finding. The SFT forward, loss, backward, and
optimizer update all happen in one Transformers/PEFT model:

```text
Transformers base + PEFT LoRA
              |
              v
      SFT forward and loss
              |
              v
         update A and B
```

There is no separate rollout engine and no actor-to-vLLM synchronization.


   `GEMMA_LORA_SCALES`.

### `inference_engine` does not mean vLLM here

The agent repository has YAML blocks named `inference_engine`, but this is a
schema belonging to its custom evaluation harness. Its fine-tuned Gemma recipe
uses:

```yaml
inference_engine:
  type: GEMMA_RAW
  base_url: http://localhost:11500
```

See
[`harness/recipes/vyra_gemma_ft.yaml`](https://github.com/oumi-ai/agent-finetune/blob/3e81f5b52623ed2244296b3cc1de0cf69d01426f/harness/recipes/vyra_gemma_ft.yaml#L38-L54).

This is distinct from an Oumi inference configuration such as:

```yaml
model:
  model_name: google/gemma-4-E2B-it
  adapter_model: /path/to/adapter

engine: VLLM
```

Oumi supports the latter configuration in general. No tracked configuration in
the inspected `agent-finetune` commit uses `engine: VLLM` or
`inference_engine.type: VLLM` for the LoRA evaluation.

### Its `adapter_model` settings are for further training

The repository does contain many `adapter_model:` fields. They occur in DPO/RPO
training configurations, where an existing SFT adapter is loaded as a trainable
PEFT model and updated further. For example:

```yaml
model:
  model_name: oumi-ai/gemma-4-E2B-it-thestage-xs-bf16
  adapter_model: oumi-ai/vyra-gemma-4-E2B-xs-lora
  adapter_trainable: true
```

See
[`gemma4_e2b_dpo_xs.yaml`](https://github.com/oumi-ai/agent-finetune/blob/3e81f5b52623ed2244296b3cc1de0cf69d01426f/training/gemma4_e2b_dpo_xs.yaml#L9-L23).
This is not a vLLM inference configuration.

### What the repository's vLLM command covers

The one concrete `vllm serve` command found in the repository is:

```bash
vllm serve runs/release_verify/checkpoints/e2b_ours_m --dtype bfloat16
```

The surrounding documentation says that `e2b_ours_m` is a materialized,
sharded, approximately 9.3 GB Hugging Face BF16 checkpoint. No LoRA adapter is
passed to vLLM. See the
[`TheStage MLX-to-HF experiment`](https://github.com/oumi-ai/agent-finetune/blob/3e81f5b52623ed2244296b3cc1de0cf69d01426f/experiments/2026-08-12-thestage-mlx-to-hf/README.md#L11-L42).

That command demonstrates that vLLM can serve the Gemma 4 architecture and a
full checkpoint. It does not exercise `--enable-lora`, `--lora-modules`,
`LoRARequest`, Oumi's `adapter_model` plus `engine: VLLM`, or runtime adapter
activation.

### Conclusion from this case study

The repository establishes all of the following:

- Gemma 4 E2B LoRA SFT works through Transformers, TRL, and PEFT.
- The PEFT adapter can be converted to GGUF.
- The converted adapter works at runtime in llama.cpp.
- A standalone Gemma 4 BF16 checkpoint can be served by vLLM.

It does **not** establish either of the following:

- An unmerged Gemma 4 adapter works through stock vLLM.
- Continually updated Gemma 4 adapters can be synchronized from a verl actor to
  vLLM during GRPO.

There is therefore no contradiction: the successful adapter evaluation uses
llama.cpp's LoRA implementation, while the GRPO blocker is in vLLM's separate
LoRA manager.
